## Method

- **Sources.** Official documentation only, plus the WAI-ARIA Authoring Practices Guide (APG) and the manuals of professional tools. In each row, a source marked **(read)** was fetched and read for this catalogue on 2026-11-07; an unmarked source is the official page named from prior knowledge and is to be checked when the component's build packet runs. No result, measurement or claim of completeness is invented; where no surveyed system ships a pattern, the row says so.
- **Tiers** ([definitions](foundation.md#tiers-what-belongs-where)): **Fundamental** is a universal building block, built from tokens only; **Compound** is an arrangement of fundamentals for a need some apps have; **Layout** is a reusable view or section with named regions. A specialist control with its own input model that few apps need is marked *Fundamental (specialist)*: it is built from tokens like a fundamental but its priority is lower.
- **Priority.** **Must**: the library is not credible without it, or the owner named it. **Should**: common across the surveyed systems or needed by a planned view. **Later**: specialist or rare; catalogued so it is not forgotten, built on a grounded need.
- **Dedupe rule.** One component per need. A row marked *variant of X* is a prop, slot or mode of X, never a second component. A row marked *cross-family* is catalogued once, in the family named.
- **Owner constraints on every row** ([brief](brief.md#design-constraints)): Switch for binary settings; no one-sided accent borders; notifications auto-dismiss unless reading must be enforced; square inner segments in any segmented bar (rounding only on the outer ends); padding at the right interior layer, edge-to-edge scrolling and unclipped focus; no redundant variants.
- **Shared size scale.** Controls take a per-instance `size`. Buttons and fields use the seven steps (`xs`, `s`, `normal`, `m`, `l`, `xl`, `xxl`, [Button](component-coverage.md#sizes)); small selection controls (Checkbox, Switch, Radio, Slider) use three (`s`, `normal`, `l`). The theme's space option changes the space around a control, never its size.
- **Shared states.** Every interactive item designs: rest, hover (pointer only), focus-visible (unclipped ring), active or dragging, disabled, read-only, invalid with a message, and, where a change is committed, the commit states pending, confirmed and failed from the [ui-states](foundation.md#craft-skills-applied) rules. Forced colours and the four token contexts (light, dark and their contrast variants) apply to all.

## Sliders and range inputs

A slider sets a value by position along a track. The research found one input model (thumbs on a track, keyboard-steppable) behind most variants, and four genuinely different models: the **allocation slider** (moving a boundary trades share between two segments), the **gradient stop editor** (stops carry colours and can be added and removed), the **colour channel slider** (the track shows the colour each value produces) and the **knob** (rotary). Everything else is a prop of one Slider.

**Dedupe decision:** one **Slider** fundamental (single, range and multi-thumb; marks; steps; orientation; origin; scale) plus four separate components for the four different models. No `RangeSlider`, `DiscreteSlider`, `VerticalSlider` or `SliderWithInput` components: those are props and slots of Slider.

### Allocation slider: the specification

The owner's example, specified because no surveyed system ships it.

| Aspect | Rule |
| --- | --- |
| Model | `segments`: an ordered list of { label, share, colour token from a `set.*` purpose }, shares summing to `total` (default 100). n segments have n − 1 boundaries. |
| Adjust | Drag a boundary: the share moves between the two neighbours only; others never change. Drag inside a segment: moves both its boundaries together where neighbours allow (the segment keeps its share and shifts) — **later**, off by default. |
| Exact entry | Each segment's share is editable as a number; typing takes from or gives to the next unlocked segment and says which. |
| Limits | `minShare` per segment (default 0, or 1 step if empty segments are not allowed); a segment can be `locked`; a boundary next to two locked segments is inactive. |
| Steps | `step` (default 1 %); shares shown rounded, sum always exact (the last unlocked segment absorbs rounding). |
| Visual | Square inner segment ends (owner rule); rounding only at the outer ends of the whole bar; boundaries are thumbs with a 24 px minimum hit area; segment labels inside when they fit, otherwise in a legend below. No one-sided accent borders. |
| Add and remove | **Later**: add a segment by splitting the selected one; remove gives its share to a neighbour. |
| Accessibility | Each boundary is a `slider` whose value is the cumulative position and whose `aria-valuetext` names both shares ("Design 40 %, Engineering 35 %"); min and max update as neighbours change (APG dependent values). Arrows move one step, Page Up/Down ten, Home/End to the neighbours' limits. The legend lists every share as text. |
| States | Rest, hover on a boundary, focus on a boundary, dragging, locked segment, at-limit (boundary cannot move further, said in text), disabled, read-only, invalid (shares do not sum, from bad data). |

### Gradient stop editor: the specification

| Aspect | Rule |
| --- | --- |
| Model | `stops`: { position 0–1, colour, optional midpoint }; at least two stops. |
| Adjust | Drag a stop to move it; stops may cross (order is by position). Click empty track to add a stop with the interpolated colour there. Delete or Backspace, or dragging a stop off the track, removes it unless only two remain. |
| Select and edit | One active stop; its colour opens the colour picker; its position is editable as a number (Blender's "Position"). An index selector reaches stops too close to grab (Blender's "Active Color Stop"). |
| Tools | Flip, distribute evenly, eyedropper (**should**); interpolation (linear default; ease, constant, B-spline **later**); colour space for interpolation (sRGB, OKLCH **later**). |
| Visual | The track shows the gradient over a checkerboard where alpha is used; each stop shows its colour as a swatch with a full outline (no one-sided border); the active stop has the selected treatment. |
| Accessibility | Each stop is a `slider` (position), `aria-valuetext` gives position and colour name or value ("30 %, #3366FF"); Enter opens its colour; Delete removes; a "Add stop" button offers the keyboard path to adding. |

### Accessibility

- Single thumb: native `input type=range` (role `slider`); multi-thumb: one `slider` per thumb, each in the tab order, tab order fixed by thumb index, never by position ([APG multi-thumb](https://www.w3.org/WAI/ARIA/apg/patterns/slider-multithumb/), read).
- `aria-valuemin`, `aria-valuemax` and `aria-valuenow` per thumb; dependent bounds updated when another thumb moves; `aria-valuetext` whenever the number alone is unclear ("Monday", "€40", "Design 40 %").
- Named by the visible label (`aria-labelledby`); range thumbs named "Minimum price" and "Maximum price"; `aria-orientation=vertical` when vertical.
- APG warns that touch screen readers may not operate custom sliders; the paired number input is the fallback path, which is why it is **must**.
- Focus ring on the thumb, never clipped by the track container; contrast 3:1 for track, fill and thumb against the surface in all four contexts; forced colours keep track and thumb visible.

## Lists and list items

A list shows items of the same kind in one column. Research separates lists by **what an item does**, because that decides the semantics and keys: nothing (a static list), navigate (a navigation list), run an action (an action list), get chosen (a selectable list) or hold its own controls (a grid list). Every surveyed system builds all of these from **one item anatomy** (leading visual, words, trailing visual or action), which is the dedupe.

**Dedupe decision:** one **List** fundamental with a `mode` (`static`, `action`, `select`, `grid`; navigation lives in the Navigation family) and one **ListItem** fundamental with slots, used by every list in the library, including the popup lists of Select and MenuButton that ListItem already serves. No `ActionList`, `ListView`, `ResourceList`, `Checklist` or `InboxList` components: they are modes, slots or examples. RowList, IndexList and DescriptionList stay compounds (named facts, page indexes, term pairs), not list modes.

### Accessibility

- Static lists are `ul` or `ol`; when markers are removed with CSS, the list keeps `role=list` so Safari still announces it.
- Action list in a menu: `role=menu` and `menuitem`; on a page, buttons in a `ul`. Selectable list: `role=listbox` and `option` with `aria-selected` and `aria-multiselectable`. Items holding controls: `role=grid` (or React Aria's GridList model), never a listbox, because options cannot contain interactive content ([APG listbox](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/), read).
- Focus by roving `tabindex` or `aria-activedescendant` (the existing ListItem supports both); the focused item scrolls into view without moving the page.
- Group headings are named groups (`role=group` with `aria-labelledby`); dividers are `role=separator` only when they separate groups.
- Reordering has a non-drag path and live-region announcements ("Moved Report to position 2 of 5").

## Badges, tags and chips

Small labelled shapes. The surveyed systems use many names (badge, lozenge, label, state label, counter, status light, tag, chip, pill, token) for two different jobs, and Fluent states the line between them: a **badge** shows information the system set and the reader cannot change; a **tag** (chip) represents a value someone picked and can change or remove ([Fluent 2, Tag](https://fluent2.microsoft.design/components/web/react/core/tag/usage), read).

**Dedupe decision:** two fundamentals. **Badge** (non-interactive: label, count, dot, status) and **Chip** (interactive: input, filter, with an optional primary action), plus **ChipGroup** for any set of chips. A read-only tag is a Badge (Carbon's read-only tag, GOV.UK tag, Atlassian lozenge, Primer label and state label are all Badges). Material 3's assist and suggestion chips are compact Buttons, not chips: they run an action, which is Button's job. No `Lozenge`, `Label`, `StateLabel`, `CounterLabel`, `StatusLight`, `Pill` or `Token` components.

### Accessibility

- Badge words are real text; a count or dot on an icon is also in the host's accessible name ("Inbox, 3 unread"); an icon-only badge has an `aria-label` ([Fluent 2](https://fluent2.microsoft.design/components/web/react/core/badge/usage), read).
- A ChipGroup is a grid of chips with one Tab stop: arrow keys move between chips, Delete or Backspace removes the focused input chip, Enter runs the primary action ([React Aria, TagGroup](https://react-spectrum.adobe.com/react-aria/TagGroup.html), read). Filter chips are checkboxes (multiple) or radios (single) in a named group.
- Remove buttons are named "Remove" plus the chip's label; after removal, a polite announcement says what was removed.
- Status and category never by colour alone: words, icon or shape carry the meaning in all four token contexts and forced colours.

## Inputs

Fields people type into. The library already has TextField (F15.2) and TextArea (F15.3); this family lists everything else a text or number entry can need, from the surveyed systems and from WCAG's input-purpose and authentication rules. Choosing from options is the next family (Selection); dates, times, colours and files are Pickers.

**Dedupe decision:** one **Field** wrapper (label, hint, error, counter) that every input uses; **TextField** carries every single-line text type through `type`, slots and options (search, password, prefix and suffix, clear, count); **NumberField** is separate because its model (a number with steps, bounds and locale formatting, `role=spinbutton`) differs; **TextArea** stays separate (multi-line). **Rating**, **OTP field**, **Tag input**, **Mentions** and **Inline edit** are separate because each has its own input model. Currency, percent, unit and quantity inputs are NumberField formats, not components. Filled, outlined and underlined appearances collapse to one appearance plus `quiet` for toolbars and tables; floating labels are skipped (the label stays visible above the field).

### Accessibility

- Every input has a visible `label`; hint and error are joined by `aria-describedby`; `aria-invalid` only after the person has had a chance to enter a value.
- Purpose tokens on personal-data fields (`autocomplete`) satisfy WCAG 1.3.5 and spare re-entry (3.3.7); paste is never blocked, including in passwords and codes (3.3.8).
- NumberField: `role=spinbutton` with `aria-valuenow`, `aria-valuemin`, `aria-valuemax` and `aria-valuetext` when formatted; Up and Down step, Page Up and Page Down step by more, Home and End go to the bounds; focus stays in the field; browser text editing keys untouched ([APG, Spin button](https://www.w3.org/WAI/ARIA/apg/patterns/spinbutton/), read).
- Rating is a radio group: arrows change the value, each option named "3 stars", the empty choice named "No rating" ([MUI, Rating radio group and accessibility](https://mui.com/material-ui/react-rating/), read).
- OTP is one input with `autocomplete=one-time-code`, named "Verification code, 6 digits"; the boxes are drawing only.
- Character count updates are announced politely after typing pauses, not on every key ([GOV.UK, Character count](https://design-system.service.gov.uk/components/character-count/)).
- The password reveal is a Button with `aria-pressed` and a label that changes ("Show password", "Hide password"); a text toggle of what is shown is not a setting, so it is not a Switch.

## Selection

Choosing from known options. The research groups selection controls by **how many options there are and whether they are all visible**: a few visible options (Checkbox, Radio, SegmentedControl, choice tiles, filter chips), a longer hidden list (Select), a list too long to scroll (Combobox with search), a hierarchy (Cascader, Tree select) and moving items between sets (Transfer). Switch stays the control for one binary setting that applies at once (owner rule).

**Dedupe decision:** **Checkbox** and **CheckboxGroup** (built F15.5), **RadioGroup**, **Switch** (built F15.6) and **SegmentedControl** (exists) stay; **Select** (built F15.4) gains `multiple`; **Combobox** is separate (typing filters, a different APG pattern); **Choice tile** is a presentation of Checkbox and Radio, not new semantics; **Cascader**, **Tree select** and **Transfer** are compounds. MUI's ToggleButtonGroup is not added: exclusive is SegmentedControl, multiple is a CheckboxGroup or filter chips, a single toggle is a Switch; a formatting toolbar's Bold and Italic wait for the owner's ruling (as in [Button types](component-coverage.md#types)). Ant's tags mode (create values while selecting) is the Combobox's `creatable`, and a standalone selectable list is List `mode=select` (family 2).

### Accessibility

- Groups are `fieldset` with `legend` (the question), hints joined to the fieldset; radio groups are one Tab stop with arrows moving and selecting ([APG, Radio group](https://www.w3.org/WAI/ARIA/apg/patterns/radio/)).
- Combobox follows the APG roles: the input has `role=combobox`, `aria-expanded`, `aria-controls` and `aria-activedescendant`; the popup is a `listbox`; Down opens, Escape closes then clears, Alt+Down opens without moving ([APG, Combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/), read).
- The number of results is announced politely after filtering ("12 results"); creating a value is announced.
- Choice tiles keep the native input inside the tile so keys and forms work; the whole tile is the hit area; the focus ring is drawn on the tile, unclipped.
- Conditionally revealed questions follow the option immediately in reading order; GOV.UK records that their appearance is not always announced, so keep them simple.

## Pickers

Controls that help choose a value with structure: a date, a time, a colour or a file. Each has a typed path (a field) and a visual path (a calendar, a colour area, a drop zone); the research is consistent that the typed path must always exist, because dates people know (birthdays) are faster typed, and visual pickers are hard for screen-reader and keyboard users.

**Dedupe decision:** **DateField** (typed, segmented or three separate fields), **Calendar** (the grid), **DatePicker** (field + Calendar in a popover, single or range, any granularity), **TimeField**, **TimePicker** (field + a list or grid of times), **ColourPicker** (built from Swatch, Colour area, Colour wheel, Colour channel slider and the hex field; the existing **ColourField** compound is its compact trigger), and **FileUpload** (button, optional drop zone, file list). Month, quarter, year and week pickers are DatePicker `granularity`, not components; Ant's "need confirm" is one rule per picker, not a prop people choose per instance; the analogue clock face is skipped (a time list does the same with fewer keys).

### Accessibility

- Calendar grid keys: arrows move by day and week, Page Up and Page Down by month, Shift with them by year, Home and End to the week's start and end; Enter chooses; month changes are announced ([APG, date picker dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/examples/datepicker-dialog/)).
- Segmented fields are a group of spinbuttons named by the field label; separate-part date fields are a fieldset with a legend ([GOV.UK, Date input](https://design-system.service.gov.uk/components/date-input/), read).
- Colour area is two sliders (x and y) and colour sliders are sliders, each with `aria-valuetext` giving a colour name and value ("dark vivid blue, #1E40AF") ([React Aria, ColorArea](https://react-spectrum.adobe.com/react-aria/ColorArea.html)).
- The file button is the native file input, named by its label; the drop zone is an enhancement, never the only path; each file's progress and result are announced politely.

## Navigation

Moving between places: pages, views, sections of a page and steps of a task. The research splits navigation into **links that change the location** (side navigation, top navigation, tabs used as navigation, breadcrumbs, pagination, table of contents, skip and back links) and **widgets that switch content in place** (tab panels, steppers, menus, command palette). The split decides the semantics: real links in a `nav` landmark for the first, APG widgets for the second, and the two are never mixed in one component.

**Dedupe decision:** **Link** (exists) for every navigating mark; **Navigation** (exists, compound) grows into the one side navigation for every width (expanded, rail, drawer on small screens) rather than separate drawer and rail components; **Tabs** is one compound with `variant` for tab panels and for page navigation; **Menu** (the popup of MenuButton) also serves context menus and menubars; one **Command palette**; **Pagination** and **Stepper** are separate. Material 3's navigation bar, rail and drawer are one Navigation in three layouts; Ant's top, inline and vertical menus are Navigation and Menu; Carbon's overflow menu is a MenuButton with an icon-only trigger.

### Accessibility

- Navigations are `nav` landmarks, each with a distinct name when there are several ("Main", "Breadcrumb", "Pagination"); links stay links; a page's own regions use landmarks so the skip link has a target.
- Tabs follow APG: one Tab stop on the tab list, arrows move between tabs (wrapping), Home and End; Tab then goes into the panel ([APG, Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/), read).
- Menus follow APG menu button and menubar keys; menus are for actions and options only, never for site navigation (use disclosure navigation, [APG](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/)).
- The command palette is a modal dialog containing a combobox and listbox; it returns focus where it was opened.
- Pagination links say what they do ("Next page", "Page 5"); the current page is marked with `aria-current` and not a link.

## Overlays

Surfaces that sit above the page: tooltips, popovers, dialogs, sheets and tours. They share one positioning engine (anchored to a trigger, flipping and shifting to stay on screen) and one top layer; the web platform now offers both natively (the `popover` attribute and `dialog` element, CSS anchor positioning), which the library uses where support allows. The research separates them by **whether they block the page** (modal) and **whether they can hold interactive content**.

**Dedupe decision:** one **Tooltip** (a short label, never interactive), one **Popover** (anchored, may be interactive; Toggletip, hover card and confirmation popover are its uses), one **Dialog** (modal or not; alert dialog and full-screen are variants), one **Sheet** (a panel from an edge: side or bottom; Material 3's side and bottom sheets, Fluent's Drawer, shadcn's Sheet and Drawer are one component), and one **Tour** (Spotlight, coach marks and teaching popovers are its steps). | Stacked | Dialog over Sheet, Popover in Dialog | Only the top one is interactive; Escape closes the top one only |

### Accessibility

- Tooltip: `role=tooltip` referenced by `aria-describedby` (or as the name of an icon-only control); appears on focus as well as hover; hoverable, persistent until dismissed, and dismissible with Escape without moving focus (WCAG 1.4.13).
- Popover: the trigger has `aria-expanded` and `aria-controls`; focus moves into the popover only when it holds controls; Escape and outside click close and return focus.
- Dialog: `aria-modal`, named by its title, described by its message; focus starts on the first sensible control (the safest action in an alert dialog); Tab cycles inside; focus returns to the trigger ([APG, Dialog (modal)](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)).
- Sheets that do not block the page are complementary regions, not dialogs; modal sheets follow the Dialog rules.
- Nothing an overlay covers may hold the keyboard focus (WCAG 2.4.11 focus not obscured); sticky headers and sheets leave the focused element visible.

## Feedback and status

Telling people what happened, what is happening and what to do next. The research finds four placements, each with its own component across the systems: **transient** messages at the edge of the screen (toast, snackbar, message, flag), **persistent** messages in the content (inline alert, banner, message bar, section message, callout), **progress** while something runs (progress bar, spinner, skeleton) and **whole-view outcomes** (empty state, result page, error summary). The project's ui-states rules already fix the transient form: one bottom notification pill, one line, at most three, auto-dismiss by default (owner rule), hard-dismiss only when reading must be enforced.

**Dedupe decision:** **Notification** (the transient pill; Toast, Snackbar, Message, Flag and Sonner collapse into it, Ant's separate "notification" card with title and description is dropped as a second transient form), **Alert** (persistent, in content: inline, section and page-wide banner placements of one component; Callout, MessageBar, Section message, Banner, Inset text, Warning text are its uses), **Error summary** (separate: it links to fields), **Progress** (one indicator: bar, ring and the compact spinner, owner's one-indicator rule), **Meter** (separate: a value in a known range, not progress), **Skeleton**, **Empty state** and **Result**.

### Accessibility

- Notifications are announced through the live announcer (`status`, polite; errors `alert`) without taking focus; their action is reachable by keyboard (a shortcut such as F6 or a landmark), and auto-dismiss pauses while focus is inside.
- Inline alerts that appear after an action are announced; static ones are plain content with a heading where useful.
- The error summary takes focus on submit, is titled "There is a problem", and each link moves focus to its field ([GOV.UK, Error summary](https://design-system.service.gov.uk/components/error-summary/)).
- Progress has `aria-valuenow`, `aria-valuemin`, `aria-valuemax` and a label; indeterminate omits the value; the owning region sets `aria-busy` and announces completion once.
- Meter uses the native `meter` element or `role=meter`, with words for the zone ("Storage almost full").
- Empty states and result pages start with a heading; their actions are Buttons or Links named by what they do.

## Data display, tables and trees

- Tables keep native `table` semantics with `caption`, `th scope`, `aria-sort`; only spreadsheet mode becomes `role=grid` with arrow keys between cells ([APG, Grid](https://www.w3.org/WAI/ARIA/apg/patterns/grid/)).

- Avatar images have the person's name as alternative text unless the name is shown beside them; group overflow says how many more and lists them.
- Statistic changes are words ("Up 12 % from last week"), not colour or arrows alone.

## Media

Images, video, audio and the controls around them. The systems ship a narrow set (image with preview, image list, carousel); pro tools (Ableton, Blender's sequencer, DaVinci Resolve, Figma) add waveforms, timelines and zoomable canvases. The web platform supplies most of the behaviour (`img` with `srcset` and lazy loading, `video` and `audio` with `track`, Picture-in-Picture, Media Session), so the library wraps native elements.

**Dedupe decision:** **Image** (fundamental; fallback, placeholder, aspect ratio, caption through `figure`); **Lightbox** (compound; zoom, rotate, gallery navigation) used by Image previews and galleries; **Image grid** (standard, quilted, masonry layouts of one component); **Carousel** (compound, owner-named); one **Media player** for video and audio sharing the controls (seek bar is the Slider with buffered range); **Waveform** and **Media timeline** for pro tools; **Compare slider** for before and after. ## Charts and data-visualisation primitives

Charts are built from a small set of **primitives** (marks, scales, axes, gridlines, legend, tooltip, annotations, interactions) and then named **chart types** that arrange them. Carbon catalogues its chart types as simple, flow and spatial ([Carbon, chart types](https://carbondesignsystem.com/data-visualization/chart-types/), read); Vega-Lite and the grammar of graphics catalogue the marks ([Vega-Lite, mark](https://vega.github.io/vega-lite/docs/mark.html)). The library already has the StackedBar compound; the owner's rule that inner segments stay square applies to every stacked or segmented mark.

**Dedupe decision:** primitives are shared fundamentals (one Axis, one Legend, one chart Tooltip, one set of marks, one colour scale per purpose from `set.*` tokens); chart types are thin compounds over them, so **grouped, stacked and 100 % stacked bars are one Bar chart**, **step and smooth lines are one Line chart** (smoothing off by default: it invents values), **area is a Line chart fill**, **donut is a Pie chart with a hole**, **bubble is a Scatter chart with size**. Gauge and meter are the Meter fundamental from Feedback. Word clouds and 3D charts are skipped.

### Sizes and density

Charts fill their container and keep a minimum readable size; below it they switch to a simpler form (fewer ticks, legend below, sparkline). Axis labels use `caption`; data labels `caption`; titles belong to the surrounding Section, not the chart. Sources: [Carbon, dashboards](https://carbondesignsystem.com/data-visualization/dashboards/); [Spectrum, data visualisation fundamentals](https://spectrum.adobe.com/page/data-visualization-fundamentals/); [Primer, data visualisation](https://primer.style/product/getting-started/foundations/data-visualization/).

### Accessibility

- Each chart has a title and a one-sentence summary of its main point, and its data as a table ([W3C, complex images](https://www.w3.org/WAI/tutorials/images/complex/)).
- Colour is never the only channel: direct labels, shapes, line styles or patterns separate series; contrast 3:1 for marks against the background in all four contexts.
- Keyboard: the chart is one Tab stop; arrows move between points and series; the tooltip shows on focus; values are announced ([Highcharts, accessibility module](https://www.highcharts.com/docs/accessibility/accessibility-module)).
- Motion on load is short and stops under reduced motion; live-updating charts do not announce every change.

## Editors

### States

| State | Applies to | Rule |
| --- | --- | --- |
| Editing, read-only, disabled | All editors | Read-only keeps selection and copy; no toolbar |

### Accessibility

- Editable regions are named `textbox` elements with `aria-multiline`; formatting is reachable from the toolbar (one Tab stop, arrows inside) and from keyboard shortcuts listed in a help dialog ([CKEditor 5, accessibility](https://ckeditor.com/docs/ckeditor5/latest/features/accessibility.html); [MDN, contenteditable](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/contenteditable)).
- Toggle formatting buttons, if approved, use `aria-pressed` and keep their label ("Bold"); they are not Switches because they act on the selection, not a setting.
- Code editors must let Tab insert indentation and offer an escape (Ctrl+M or Escape then Tab) to leave the editor ([CodeMirror](https://codemirror.net/docs/)).
- Canvas, curve and node editors give every object a keyboard path: select by Tab or a list, move with arrows, and an outline or layers list as the accessible structure.

## Layout tier

Reusable views and sections with named regions ([tier 3](foundation.md#tiers-what-belongs-where)). The owner named the first set (article, list of articles, list of sponsors, image gallery with hero, bento, documentation, e-commerce, checkout, first-run onboarding); the research adds the canonical app layouts (list-detail, supporting pane, feed), the government-tested page patterns (question pages, check answers, confirmation, task list, error pages), app shells and pro-tool workspaces. Below them, a few more **arrangement primitives** join Stack, Cluster and Grid as fundamentals, because every layout needs them and they hold no content of their own.

**Dedupe decision:** arrangement primitives follow the "Every Layout" set so each layout is composed, not hand-styled: **Sidebar**, **Switcher**, **Center**, **Cover**, **Frame**, **Reel**, plus **Splitter** (resizable panes) and **Masonry**. Layouts are data-driven views over compounds: one **App shell** (with or without side navigation and an end panel), one **Page layout** (exists), one **List-detail** layout, and a library of page and section layouts. Marketing sections (hero, features, pricing, testimonials, logos, FAQ, call to action) are Layout sections, not compounds, because they are reusable sections of a view.

### Rules for every layout

- Regions are landmarks (`header`, `nav`, `main`, `aside`, `footer`) with names where there are several ([APG, landmark regions](https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/)); reading order follows source order at every width.
- Padding lives at the region's interior layer; scroll regions reach the surface edge with the scrollbar at the edge; focus is never clipped (owner rules).
- Every layout is assembled from data (regions, sections, items) and has no styles of its own beyond its grid; products make their own layouts beside these.
- Each layout lists its loading (section skeletons), empty and error states per region, and how it adapts from 320 px to wide screens.

## Actions and buttons

## Typography, content and utilities

The text components and the invisible plumbing every other component relies on. Text, Heading, Link, Code, List and Icon exist; this family adds what content-heavy pages and robust components still need, and the utilities (top layer, focus scope, visually hidden text, direction and locale) that should exist once rather than be re-implemented inside each component.

**Dedupe decision:** **Prose** styles rich content (Markdown or CMS HTML) with the same tokens as Text and Heading, instead of a second set of typographic components; formatting of numbers, dates, lists and relative time goes through one locale layer (`Intl`); **Form** is the compound that arranges Fields and the submit row; utilities are internal building blocks exported for products, not visual components.

### Accessibility

- Text resizes to 200 % and reflows at 320 px without loss; text spacing overrides do not break components ([WCAG 2.2, resize text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html); [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html); [text spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)).
- Headings follow the outline, never chosen for size; one `h1` per page.
- Links are underlined in running text; colour alone never marks a link.

## AI and conversation

Interfaces for generated content and chat with assistants and agents, now common enough that design systems ship them: Carbon has an **AI label** and AI guidelines, Fluent has Copilot components, Primer has AI patterns, and AI SDK Elements catalogues the building blocks of chat, agent and voice interfaces. Human-AI interaction guidelines (Microsoft HAX, Google PAIR) set the behaviour: show what is generated, why, how sure, and let people correct it.

**Dedupe decision:** one **Conversation** compound (message list as a log, messages, prompt input) whose parts are reused by agent and voice products; one **AI label** (Badge-like marker that opens an explanation popover); reasoning, tool calls, plans and tasks are one **Disclosure step** pattern with a status; sources and inline citations are Links with a source list; feedback is a RadioGroup of icon options; model choice is a Select; generated-content shimmer is the Skeleton. Nothing here becomes a second Button, Badge or Progress.

### States and accessibility

- States per message: sending, streaming, stopped, complete, failed (Retry keeps the prompt), edited; per step: queued, running, needs approval, done, failed.
- The message list is a `log`: new complete messages are announced politely; streaming tokens are not announced one by one.
- Focus stays in the prompt after sending; Escape stops generation; every action on a message is a named Button reachable by keyboard.
- AI-generated content is labelled in text, not only by icon; errors say what to do next, and generated content never replaces the reader's input without consent.
