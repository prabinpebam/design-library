# Design Library: project brief

> **TL;DR:** Build one robust, adaptable frontend foundation that AI agents can customize through clear contracts, not forks or improvised styles. Strong fundamentals and explicit abstraction levels should support many kinds of web UI. "Universal", "perfect" and "easiest for AI" are ambitions to validate, not achieved claims. This increment is the Slate project draft, not frontend implementation.

## Vision and users

The owner's ambition is a design system so flexible and scalable that another design system is not needed: one frontend library can be themed and customized into the required web UI. AI agents are first-class builders because future customization is intended to happen through them.

The product serves people specifying and reviewing interfaces, developers integrating them, and agents generating or changing them. Its advantage should be reusable behavior, understandable boundaries and safe customization, not a growing catalogue of near-duplicate components. A supported interface should change brand or layout without changing the meaning of controls, discarding accessibility or rewriting fundamentals.

"Universal" means expanding proven coverage across declared interface families, not claiming every possible UI has already been handled. "Easiest" means measurable agent task success and lower correction effort against a declared baseline. The initial validation matrix and acceptance targets below are proposed working defaults for review.

## Promise and scope

| ID | Promise | What breaks it |
| --- | --- | --- |
| P1 | People and agents can reuse consistent, accessible components rather than reinvent behavior and styling for each view. | Ad hoc styles, duplicated variants, inaccessible states or inconsistent behavior. |
| P2 | Every design decision and quality claim can be traced to intent and inspectable evidence. | A claim of "perfect" without tests, observations or measurements; documentation drifting from source. |
| P3 | One frontend foundation can adapt to distinct brands and supported web UI families without replacing its behavioral fundamentals. | A theme requires a component fork, another design system, or an untracked style escape; the same control behaves differently across brands. |
| P4 | Agents can discover the supported contract, produce valid customizations and explain changes without guessing hidden conventions. | Ambiguous APIs, undocumented variants, invalid data accepted silently, or repeated repair loops that make agents less reliable than the declared baseline. |

These are intended product promises, not achieved capabilities. The authorized outcome now includes the expanded universal, AI-first Slate brief and proposed success criteria. It does not authorize an implemented frontend framework, large component inventory, deployment or publication.

**Not promised by this draft:** a replacement for every host runtime or backend, support for every unknown interaction on day one, unlimited arbitrary styling, or demonstrated superiority over all frontend frameworks. The goal is one extensible foundation whose declared coverage grows without breaking its contracts. A required behavior outside that coverage is surfaced as a design-system gap, not hidden with a fork.

## Intended flow and architecture

<ol class="slate-steps">
  <li class="slate-step"><p class="slate-step__title">Ground the use case</p><p>Promise and job identify the user-can statement and task flow.</p></li>
  <li class="slate-step"><p class="slate-step__title">Reuse before adding</p><p>Check existing tokens and tiers; add a component only for a distinct unmet need.</p></li>
  <li class="slate-step"><p class="slate-step__title">Inspect every state</p><p>Review behavior, copy, focus, waits and recovery in representative contexts.</p></li>
  <li class="slate-step"><p class="slate-step__title">Record the evidence</p><p>Generate library documentation from source and update the spec and quality rows.</p></li>
</ol>

Proposed architecture follows Craft: tier 0 tokens/foundations and pure behavior; tier 1 sealed fundamentals; tier 2 compounds; tier 3 layouts; views mapped from validated data. Dependencies point downward, not sideways/upward. W3C DTCG 2025.10 tokens have descriptions, semantic/component ownership and light, dark and contrast contexts. Generated output must not be edited by hand.

The installed design-system skill ([pinned upstream contract](https://github.com/prabinpebam/agentic-craft/blob/8dd2576f41763a9add9863852697fd3961699019/skills/design-system/SKILL.md)) is the authority for this intended structure. Choose actual source directories, renderer/framework and the first user flow in stage 1; none exists yet. Slate's generated reader and bundled Canvas are upstream documentation capability, not newly built product components.

## Abstraction boundaries

| Level | Responsibility | Customization boundary | Must remain true |
| --- | --- | --- | --- |
| 0: tokens and foundations | Semantic design decisions, icons as data, pure behavior, keyboard models and geometry. | Versioned theme/context tokens; primitive palette remains private to semantic resolution. | No upward dependency; contrast and ownership invariants hold. |
| 1: fundamentals | Small native-first controls with typed contracts and complete behavior/states. | Documented semantic props and owned token aliases, not arbitrary class/style injection. | Fundamentals stay sealed; a visual theme never changes control meaning. |
| 2: compounds | Reusable combinations that express one distinct need. | Composition through supported slots/props using lower tiers. | No compound-to-compound imports or restyling lower-tier internals. |
| 3: layouts | Reusable screen structures with named regions and space ownership. | Choose layouts and populate their regions; add a new layout only for a proven unmet structure. | No layout nesting or scattered leaf padding; full-bleed scrolling and focus remain possible. |
| Views and content | Validated data mapped to the registry and layouts. | Content, order, navigation, state and registered action references as typed data. | No per-view styles, arbitrary executable data or unknown types accepted at render time. |
| Integration boundary | Host platform, data/store wiring and renderer adapters. | Explicit trusted adapters chosen after feasibility evidence. | Domain logic is not smuggled into style tokens; the framework choice is not made by this draft. |

Every new abstraction must explain the concrete variation it absorbs and the simpler alternative it avoids. Shared behavior belongs below components; styling belongs in tokens; composition belongs in supported slots and view data. Generality is earned by repeated needs, not a generic "options" bag or a configurable prop for every pixel.

## Theming and customization model

<ol class="slate-steps">
  <li class="slate-step"><p class="slate-step__title">Declare a supported theme/context</p><p>Choose brand, typography, density and allowed shape/motion roles; preserve light, dark, contrast and reduced-motion requirements.</p></li>
  <li class="slate-step"><p class="slate-step__title">Resolve semantic contracts</p><p>Validated token aliases produce generated output. Components read semantic roles and their own owned tokens, not raw values or another component's internals.</p></li>
  <li class="slate-step"><p class="slate-step__title">Compose supported structures</p><p>Layouts and registry entries map validated view data to existing fundamentals and compounds. A new need is evaluated at the lowest useful tier.</p></li>
  <li class="slate-step"><p class="slate-step__title">Review the affected contexts</p><p>Inspect the proposed change and consumers; reject invalid customization before replacing the current working configuration.</p></li>
</ol>

**F1: adapt a product (U4, U7).** Identify the scope (one view, selected views, or whole product), choose the documented theme/layout changes, preview affected contexts, then accept or reject the proposal. Mixed selections report differing values rather than inventing a shared setting. Unsupported combinations explain the failing contract and how to recover; cancellation retains the previous version. A new brand changes appearance through supported tokens, not keyboard behavior, labels or persistence semantics.

The first proposed coverage matrix contains three deliberately different UI families: task/form-heavy applications, content/marketing interfaces, and data-dense analytical views. For each, compare two visibly distinct brand configurations across light, dark and more-contrast contexts. These are candidate validation fixtures, not implemented demos or an exhaustive claim of universality. Expansion follows unmet jobs and evidence, not catalogue breadth.

## Optional add-ons and integrations

**Add-ons are optional, removable, higher-level integrations above the core, not a new dependency inside its tiers.** P3/J6/U8 motivates them. The core must work fully without any add-on: readable solid surfaces, ordinary elevation, input, focus, states and content cannot depend on lighting or glass. A disabled add-on must load no effect engine/assets and leave no observers, animation loops, filters or settings that corrupt the core.

<ol class="slate-steps">
  <li class="slate-step"><p class="slate-step__title">Core: tokens to sealed components</p><p>Tier 0 decisions feed fundamentals, compounds and layouts. Validated view data composes the result; no core tier imports an add-on.</p></li>
  <li class="slate-step"><p class="slate-step__title">Public seams: one integration boundary</p><p>Expose documented semantic/component tokens, registered layout/surface slots, theme contexts and view data. Adapters use only these seams, never private markup or another component's owned tokens.</p></li>
  <li class="slate-step"><p class="slate-step__title">Add-ons: opt in above the core</p><p>A registered adapter applies an effect to declared host surfaces. Scope and context select it; disabling or removing it returns to the ordinary core.</p></li>
</ol>

| Contract | Proposed requirement |
| --- | --- |
| Registration | Versioned descriptor: stable ID, adapter version, compatible core/schema range, public seams read/set, owned token namespace, resources and licence/attribution. Executable modules come from a trusted registry, never arbitrary executable view data. |
| Ownership | Read exported semantic roles or explicitly exported component aliases only. Set owned add-on tokens/context configuration and registered host wrappers/slots; no fundamental forks, private DOM selectors or global style escape. |
| Scope | Enable/disable per subtree and theme context, including one view, selected views and all views. Nearest explicit scope wins; user accessibility preferences override visual settings. No forced global activation. |
| Lifecycle | Mount/update/dispose through the host boundary; release resources on removal. Reject incompatible versions or overlapping ownership before applying changes; keep the previous working configuration. |
| Declaration | State supported browsers, unsupported combinations, solid/no-effect fallback, accessibility impact and measured performance cost. Source documentation must distinguish upstream capability from the adapter's unproven fit. |
| Restraint | The owner is considering an explicit optional material treatment, not authorizing decoration throughout the core. Effects must communicate a reviewed spatial/material hierarchy; no redundant shadows, glass-on-glass or one-sided accent borders. Approved fundamentals retain their ordinary look when the add-on is off. |

**Feasibility gap, not an escape hatch:** UI Lighting's upstream host contract currently operates on `html`/`body`, root settings, a body-level layer and `data-elevation` surfaces. It is not proven to isolate arbitrary subtrees. Its rim styles also need review against sealed fundamentals and owned elevation tokens. Liquid Glass's `filter` mode is not permission to distort readable foreground content.

| Context / failure | Required fallback and evidence for either adapter |
| --- | --- |
| Reduced transparency | Solid opaque core surface, no refraction/backdrop-filter; honour the media preference where supported and provide an explicit persisted preference otherwise. |
| Reduced motion | No moving gobo, drifting light or effect animation; keep interaction feedback and timing, not gratuitous movement. |
| Forced colours / high contrast | Disable visual effect/rims and use core system-colour/contrast tokens. UI Lighting already documents disabling for more contrast, forced colours and print; verify the adapter preserves it. |
| Text, icons and focus over changing surfaces | Measure worst-case composited contrast in light, dark and contrast contexts: all text roles at least 4.5:1; identifying non-text/focus cues at least 3:1. Include moving backgrounds and active/disabled/error states; use solid backing or reject the effect when the floor cannot be maintained. |
| Missing WebGL2, context loss or unsupported filters | UI Lighting documents rims-only without WebGL2; the product's safe default is ordinary core elevation, with no partial effect unless separately accepted. Liquid Glass's SVG backdrop mode is Chromium-only according to its core README; upstream blur fallback is not enough when transparency/contrast is unsafe, so use solid core surfaces. |
| GPU/compositing pressure | Measure map generation, backdrop-filter area, layer count, animation/scroll cost and disposal. Lazy-load only on opt-in; pause offscreen/idle work. If budgets fail, reduce scope or disable the effect, preserving input/focus. No unmeasured claim of "GPU acceleration" as a performance guarantee. |

**F4: apply/remove an effect (U8, U11).** Select one/selected/all views and a permitted context; inspect compatibility, licence and fallback declarations; preview the proposed effect and affected contexts; accept or reject. Mixed selections expose differing settings. Invalid scope/version/contrast retains the current configuration and names the failing contract with an action to disable, choose solid surfaces or revise scope. Cancel leaves the previous version; removal disposes the adapter, preserves content/actions/focus and restores core tokens. Loading an optional engine must acknowledge within 100 ms and retain the old solid view; name a wait after 300 ms, keep input usable, and offer cancellation/recovery for longer loading. Preference changes use Switch and local confirmation, not button toggles.

## Typography sources and provider contract

**Free** means licensed for commercial web use at no fee, with embedding, self-hosting, redistribution and modification rights recorded separately. Zero price does not imply an open licence, unlimited redistribution or permission to use a font in a multi-user design tool. The core supports any family meeting the declared use-case/licence policy; Google Fonts is first-class, not the only catalogue.

Typography tokens cover family/stack, role-specific size/weight/leading/tracking, supported variable axes, script coverage and fallback metrics. The generated font-face configuration consumes metric data for [`size-adjust`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@font-face/size-adjust), ascent/descent/line-gap overrides; it must not pretend different families have identical glyph widths. Typed provider/asset/metric records extend the token build's registry rather than embedding executable loaders in DTCG tokens. Unsupported metric descriptors retain a tested readable fallback.

**Delivery recommendation:** self-host versioned WOFF2 by default; choose only required languages/weights, subset only where permitted, compare variable-font bytes against needed static weights, use `font-display: swap` with matched fallback metrics, and preload only a genuinely critical face/subset. Never block content on fonts or preload every family. Fontsource npm downloads follow the Microsoft proxy; CDN delivery is a separate runtime/privacy decision, not a package-feed bypass. Google Fonts CDN makes third-party requests and can create personal-data/GDPR obligations; do not treat free access as consent or a universal compliance guarantee. Bunny is an alternative to evaluate, not automatic clearance.

Proposed reference budgets, not measured results: initial font transfer at most 100 KB compressed for the chosen initial script/weights; font-attributable CLS at most 0.02 and total CLS at most 0.1; LCP at most 2.5 s and INP at most 200 ms at p75 on the declared desktop/throttled-phone profiles. Additional scripts need separately declared subsets/budgets, not missing glyphs hidden to meet a Latin-only byte cap. The [web-font performance guidance](https://web.dev/articles/font-best-practices) explains delayed text, connection costs and font-swap layout shifts; actual baselines wait for an approved implementation.

**F5: swap typography/icons (U9-U11).** Select scope and provider/theme data; validate family script/weight availability, semantic icon coverage and licence manifest; preview text wrapping, icon meaning and affected contexts; accept/reject the versioned proposal. Font load failure/offline keeps readable system-stack text and reports the provider failure with Retry or Use system fonts. Invalid/missing icons block acceptance with the gap map, never a random lookalike. During loading keep the old view and input; cancel or stale data preserves the previous configuration. The same semantic diff/validation result serves agents in F2.

| Concern | Adapter/core rule |
| --- | --- |
| Coverage | Maintain a semantic-name x provider x size/style/direction matrix. A missing glyph is a named gap with a reviewed semantic fallback or unavailable choice; never silently change an action's meaning. Registry validation reports the path/reason/recovery. |

## The library presents itself

**Part A: proposed architecture, not an implemented library app.** P1/P2/P4 and J8/U12/U13 require a truthful self-presenting reference, not a second UI toolkit whose styling happens to resemble the library. Slate remains the independent project reasoning surface. The future **library app** is an ordinary consumer of the Design Library, with stable presentation and isolated candidate specimens.

### The circularity and the failure cases

| Failure | Why "use the library for its docs" is insufficient | Chosen boundary |
| --- | --- | --- |
| Nothing exists to present the first component | A complete explorer cannot be a prerequisite for implementing its first fundamental. | Slate holds strict-design mockups/specs first; a tiny approved consumer seeds the explorer incrementally. |
| Working-copy breakage destroys its own diagnostic UI | A token/compiler/runtime error could blank navigation and the error component itself. | Serve an immutable known-good frame independently of candidate compilation; retain plain-HTML diagnostics outside both renderers. |
| Frame theme leaks into specimens, or vice versa | Inherited CSS, root variables, fonts, portals and reset rules can make a story look right only in the explorer. | Separate documents with explicit specimen contexts; no frame styles injected into specimen documents. |
| Doc-only CSS makes the example lie | A polished docs wrapper can conceal missing padding, focus, states or tokens in the shipped component. | Same renderer/build output/story fixture as a product; no specimen overrides or hand-authored replacement examples. |
| Storybook/Docusaurus-style chrome becomes a competing system | Another visible component vocabulary recreates the exact "which library presents the library?" confusion. | Reject third-party docs UI chrome as the reference app. A headless build/extraction utility is acceptable only if it contributes no competing widgets/styles/runtime contracts. |
| Catalogue and source drift | Hand-maintained prop tables and agent instructions silently describe different APIs. | One generated, versioned machine-readable catalogue per build, consumed by both app and agents; invalid/stale output blocks candidate publication. |

The generated catalogue is a **single source per version**, not a mutable global "latest" blob. The frame declares supported catalogue/protocol schema ranges. It may inspect a newer compatible candidate catalogue while its own chrome uses the approved library build. Incompatible, malformed or missing catalogue data retains the previous reference and returns a structured `path / reason / recovery`; it never renders half a catalogue or silently labels stale data current. Agents receive the identical versioned catalogue or validation error.

**Library-app tooling is an above-core consumer layer**, not a new core tier: prop playground = schema-driven fields; token inspector = token data and approved swatch/scale representations; context matrix = registered layout regions; code view = genuine story/source text in supported code primitives. Core never imports this layer. No doc-specific widget is added to core merely to ship the explorer. A missing genuinely reusable Table, Tabs, CodeBlock or split-region capability is grounded against the library's need and a representative product job, reviewed, and added at its lowest valid core tier. Otherwise compose existing public capabilities or defer the tool. A Library layout never nests another layout, and compounds still cannot import compounds.

The specimen host's iframe is a controlled platform adapter in a registered surface slot, not an alternative styled widget or raw HTML in a view spec. Public layout/surface tokens own its geometry; no arbitrary class/style props are opened on fundamentals. All visible explorer controls use the core. Internal source-path/code inspection does not grant agents permission to depend on those internals.

### Stable frame and working specimens

| Isolation choice | Strength | Limitation | Working default |
| --- | --- | --- | --- |
| Separate iframe document per active story/context | Independent CSS variables, reset, theme, font/style loading and renderer globals; candidate errors do not replace frame DOM. | Separate focus/keyboard boundary and loading; portals stay inside the document; more documents cost memory. A renderer hang may still share browser resources, so this is not a guaranteed process/security boundary. | **Choose.** Lazy-mount a bounded visible/selected matrix, with an explicit expanded comparison when needed; never mount the entire Cartesian product. |
| Shadow DOM | Stronger selector encapsulation than ordinary descendants; relatively lightweight. | Inherited custom properties, fonts and document-wide scripts/portals still need explicit handling; no reliable JS-failure boundary. | Useful for a future embedded example, not the primary candidate isolation model. |
| Same-document scoped roots | Cheapest composition, fewer focus boundaries. | Reset/global CSS/theme/portal collisions and exceptions can falsify fidelity; failed script state is shared. | Reject for working-copy specimens beside approved chrome. |

Frame assets, catalogue and approved specimens live in an immutable last-approved artifact; rebuilding a candidate must not overwrite those files. Candidate documents use separately versioned asset URLs, their own generated tokens, `color-scheme`, brand/density/direction and viewport; no parent stylesheet or theme inheritance bridge. Frame navigation/search continue when one candidate import/render fails. Candidate state reports identify the story, build, source path, reason and actions: Retry candidate, open approved specimen, or open diagnostics; preserve selection, query, proposed props and previous readable metadata.

Communication is a minimal versioned ready/error/size/selection protocol, with exact allowed origins, story/build IDs and payload validation; no arbitrary commands, HTML or style messages. A same-origin iframe is **not** a security sandbox for hostile code. Use a separate loopback specimen origin where needed, constrain sandbox permissions to the story's declared capabilities, and never permit top navigation. Stories use synthetic data, not credentials/owner storage. Cross-document keyboard order, accessible iframe titles, focus restoration and an Open specimen alone action are part of the reviewed design. Event listeners and frame resources are disposed on removal.

Keep the frame while a specimen loads: immediate local acknowledgement, named wait rather than blanking navigation, cancel/unmount for stalled candidates and a retained approved alternative. If the frame's own artifact or token loading fails entirely, a separately served **zero-dependency plain-HTML diagnostic page** uses native headings, text, lists and links, no library, Slate, fonts, CSS or JavaScript dependency. It names the failed build/path/reason and recovery: reopen the last approved artifact, inspect a local log, or read the Slate plan. It is an emergency fault notice, not another design system or a substitute component catalogue. Neither browser-level hangs nor a stopped server can be fixed by an in-page error component; recovery must also work outside the candidate page.

**Promotion is approval, not automatic HMR:** record the owner's explicit dated words, exact candidate/artifact digest, contexts seen and any excluded behavior. Design approval permits only its specified next mode; promoting an experimental preview does not declare it production-ready. Preserve unchanged approved chrome while testing candidate component changes. A frame update is itself a bounded reviewed consumer change; generate the new coherent artifact and atomically switch its pointer only after scoped approval/evidence. Partial approval promotes only a separately built artifact containing approved changes, never the whole mixed working tree.

## Adoption and evolution

**F0: first use (U1-U3, U5).** Find the source-derived catalogue, identify the supported library/schema version, choose an example matching the intended job and context, and inspect its states/keyboard contract before producing a view proposal. Changes that reopen behavior or visual design return to the owner-approval boundary before implementation.

## Design constraints

Owner requirements apply to future product components:

- Never use a one-sided accent border on a card, button, callout or navigation. Use fills, tints, full outlines, icons or badges where information warrants them.
- Binary settings use a **Switch**, never a button impersonating an on/off toggle. Exception by owner decision (O41, 2026-11-07): the library's title bar chooses colour scheme and contrast with icon-only SegmentedControls and opens Revisions with an icon disclosure Button; settings forms still use Switch.
- Internal segments of stacked/segmented bars remain square. Rounding, if any, is only at the outer ends of the whole bar.
- Put padding once at the appropriate interior layer, usually one or two levels below a visual wrapper, not around every leaf. Scroll regions can reach the surface edge; focus rings must not be clipped.
- Provide one component variant per distinct need; reuse and deduplicate before adding another indicator or pattern.
- Notifications auto-dismiss by default. Manual dismissal is reserved for information the person must be forced to read.
- Native semantics first; target WCAG 2.2 AA, keyboard/screen-reader support, visible focus, 44 px hit targets, reduced motion and no unintended horizontal scrolling at 320 px.
- Include rest, hover, active, focus, disabled, loading, empty and error states where applicable. State feedback is local and honest; preserve input and provide recovery.
- Use the installed spacing, visual-noise, UI-copy, UI-states and perceived-performance contracts. Plan from the grounded chain; inspect views against Nielsen H1-H10, not as a replacement for user intent.

These constraints are documented intent. No claim is made that every upstream Slate interface already conforms to product-specific preferences; this setup does not fork or restyle the generic reader.
